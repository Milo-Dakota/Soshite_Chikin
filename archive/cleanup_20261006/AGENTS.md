# 『そして〖只因｜チキン〗もいなくなった』
## 《无只因生还》视觉小说项目 — Agent 工作规范

---

# 1. 项目名称

中文原作标题：

> **《无只因生还》**

日语视觉小说正式标题：

> **『そして〖只因｜チキン〗もいなくなった』**

其中：

```text
只因
```

必须保留为汉字。

其日语 Ruby / Furigana 读音为：

```text
チキン
```

即：

```text
〖只因｜チキン〗
```

该标题是本项目的重要核心梗之一，不得擅自改写成普通日语。

---

# 2. 标题梗的含义

Agent 必须理解该标题并不是普通翻译。

原作标题《无只因生还》同时包含：

1. 对《无人生还》标题结构的恶搞
2. 小说中大量死亡事件带来的“无人幸存”意象
3. “只因”与“鸡”近似发音产生的网络梗
4. 与“只因你太美 / 鸡你太美”相关的梗
5. 与中分、背带裤等反复出现的视觉元素相关联

日语标题因此并不将“只因”翻译成正常日语词。

而是故意采用：

> **そして〖只因｜チキン〗もいなくなった**

使其在视觉上保持“只因”，但在日语中读作“チキン”。

这种：

> 看起来一本正经，但细看非常荒谬

的气质，是本项目整体创作方向的重要参考。

---

# 3. 项目目标

本项目将中文接龙小说《无只因生还》改编为一部：

> **完全线性、无剧情选择、以徐启星为叙事中心、日语角色配音、中文汉化字幕的日式视觉小说。**

技术方案：

- 游戏引擎：Ren'Py
- 角色配音：Style-Bert-VITS2
- 图片素材：由 Agent 使用图像生成能力制作
- BGM / SE：使用许可明确的免费素材
- 日语台本、演出规划、图片生成、Ren'Py 实装：主要由 Agent 完成

最终作品应给人一种：

> 《无只因生还》真的曾经被某个日本厂商认真改编成 Galgame，随后又被中文汉化组汉化回来。

的感觉。

---

# 4. 整体创作气质

本项目的核心不是单纯搞笑。

相反：

> **越荒谬的原作内容，越应该认真制作。**

不要把梗主动做成低成本 meme 演出。

例如：

- 中分
- 背带裤
- “只因”
- 艾昆剧院
- 极其荒诞的剧情转折

都应该以：

> 正式商业视觉小说般的认真态度

进行演出。

笑点应来自：

> 内容本身荒谬，但作品却非常认真。

而不是：

> 游戏主动告诉玩家“这里很好笑”。

---

# 5. 最重要的改编原则

始终遵守：

> **剧情事实忠实，表现方式自由。**

必须保留：

- 主要剧情事件
- 人物关系
- 人物身份
- 世界观设定
- 重要伏笔
- 伏笔回收
- 关键笑点
- 网络梗
- 重要道具
- 重要地点
- 接龙作品造成的荒诞感
- 原作突兀但有趣的风格变化

不得为了让故事更“正常”而自行修正。

允许自由调整：

- 台词措辞
- 语序
- 台词长度
- 日语表达
- 人物口癖
- 内心活动
- 文本拆分
- 动作表现
- 表情
- 镜头
- BGM
- SE
- CG
- Scene 节奏
- 转场方式

---

# 6. 原始小说

小说原文固定放置：

```text
/source/novel.txt
```

该文件是项目最高级剧情事实来源。

禁止直接修改。

---

# 7. Narrative POV 与 Visual POV

这是项目的重要规则。

## Narrative POV

文字叙事采用：

> **徐启星中心的第一人称视觉小说叙事。**

## Visual POV

画面演出采用：

> **自由镜头。**

两者不得混淆。

---

# 8. Narrative POV

普通 Scene 的正文主要由：

```text
徐启星说出口的话
徐启星的内心活动
其他人物说出口的话
```

构成。

正常情况下：

> 不设置长期存在的第三人称小说旁白。

---

# 9. 原小说旁白的处理

原小说中的第三人称叙述不应机械复制进游戏。

依次考虑：

```text
能否直接用画面表现？
↓
能否用表情 / 动作表现？
↓
能否用 BGM / SE 表现？
↓
能否改写成徐启星的内心活动？
↓
能否通过人物对白表达？
↓
是否真的还需要文字？
```

例如原文：

> 千夏红着脸低下了头。

视觉小说可以直接：

```text
千夏切换 embarrassed 表情
轻微低头动作
短暂停顿
```

无需文字。

也可以根据需要写成徐启星内心：

```text
……脸红了？
```

---

# 10. 不要机械第一人称化

禁止大量写：

```text
我看到……
我发现……
我注意到……
我听见……
```

例如：

错误：

```text
我看到千夏低下了头。
我注意到她的手在发抖。
```

更自然：

```text
……又低下头了。

她的手在发抖。
```

或者直接依靠画面，不显示任何文字。

---

# 11. Visual POV

画面并不等于徐启星的眼睛。

Visual POV 完全自由。

允许：

- 徐启星立绘
- 千夏立绘
- 两人同时出现在画面中
- 多人物同框
- 徐启星单人 CG
- 双人 CG
- 群像 CG
- 正面镜头
- 侧面镜头
- 远景
- 近景
- 俯拍
- 仰拍
- 电影化构图

判断镜头时应问：

> 什么画面最适合这一刻？

而不是：

> 徐启星本人能不能看到自己？

---

# 12. 徐启星是完整视觉角色

徐启星必须拥有：

- 正式角色设计
- Reference
- 立绘
- 表情
- 服装
- 必要 CG

他可以正常参与视觉演出。

Narrative POV 不限制徐启星出现在画面中。

---

# 13. 配音规则

默认：

```text
徐启星对白
→ 显示文字
→ 不配音

徐启星内心
→ 显示文字
→ 不配音

其他角色对白
→ 显示文字
→ 日语配音
```

不设置普通旁白 voice。

---

# 14. 非徐启星在场剧情

原作中存在徐启星不在场的重要内容。

不得因为 Narrative POV 而删除。

可以采用：

- Side Scene
- 幕间
- 特殊章节
- 回忆
- 独立事件片段

特殊 Scene 可以暂时改变 Narrative POV。

但应明确标记。

---

# 15. Agent 总体工作方式

采用：

> **全文理解 + 逐章制作**

而不是一次性制作整部游戏。

第一次进入工程：

```text

```

必须读完整小说。

重点理解：

- 整体剧情
- 时间线
- 主要人物
- 人物关系
- 世界观
- 主要地点
- 重要伏笔
- 伏笔回收
- 反复出现的笑点
- 网络梗
- 人物关系变化
- 风格变化
- 徐启星不在场的重要剧情
- 原作中不能被合理化修正的荒诞内容

此时不要：

# 21. 第二阶段：视觉风格

正式制作 Chapter 1 前建立：

```text
/docs/visual_style.md
```

整体目标：

> 正经的日本商业视觉小说。

可参考方向：

```text
2010—2016 年左右 PC Galgame 氛围
16:9
精致二次元角色
相对克制的配色
统一日系动画背景
避免现代手游宣传图式过度高饱和
```

---

# 22. “认真制作荒谬内容”

Visual Style 必须服务于这一原则。

例如：

如果梅川备代穿着背带裤、梳着中分正式登场：

不要画成：

> 故意变形的 meme 图。

而应该画成：

> 一个真正被商业 Galgame 美术团队认真设计出来的角色。

他的：

- 中分
- 背带裤
- 姿态
- 表情

可以荒谬。

但：

> 绘画质量不能荒谬。

# 23. 图片素材由 Agent 实际生成

Agent 负责实际生成：

- 角色 Reference

- 表情差分
- 服装差分
- 背景

- 特殊剧情图

# 25. 角色 Reference

主要角色大量出图前应先建立固定 Reference。

至少包括：

- 脸型

- 发色
- 眼睛
- 年龄感
- 身材
- 身高比例
- 常用服装
- 配色
- 整体气质

后续素材应持续参考已有 Reference。

# 26. 图片一致性

一致性来自：

不是来自：

不配音。

# 33. 正常 Scene 不使用 narrator

普通徐启星 POV Scene：

> 不设置独立 narrator。

必须将小说旁白转化为：

- 画面
- 动作
- 表情
- 内心
- 对白
- 音效
- BGM
- CG

---

# 34. 日语不是逐字翻译

日语台本需要先理解：

- 角色意图
- 人物关系
- 当前情绪
- 剧情作用
- 上下文
- 人物语言特点

然后按照：

> 如果这原本就是日本视觉小说，它会怎么写？

重新组织。

---

# 35. 梗的日语化原则

网络梗不应简单删除，也不应机械直译。

遇到梗时，应判断：

```text
原梗靠什么成立？
```

可能是：

- 发音
- 汉字
- 谐音
- 人物造型
- 固定句式
- 文化背景
- 重复出现产生的笑点

如果直接翻译会失去梗：

> 可以采用日语视觉小说常见的特殊读音、Ruby、双关、视觉演出等手段重新构造。

但不得擅自替换成完全无关的日本网络梗。

---

# 36. Ruby / Furigana

Ren'Py 支持 Ruby / Furigana。

本项目可以主动利用该功能进行：

- 汉字注音
- 双关
- 特殊读法
- 梗的本地化

例如正式标题：

```text
そして〖只因｜チキン〗もいなくなった
```

应显示为：

```text
      チキン
そして 只因 もいなくなった
```

“只因”是视觉文本。

“チキン”是其日语读法。

---

# 37. Ruby 的使用原则

Ruby 不只用于普通假名读音。

本项目可以把它当作一种：

> 日式视觉小说语言演出工具。

但不要滥用。

只有在：

- 特殊读法
- 谐音梗
- 双重含义
- 标题
- 重要专有名词

确实受益时使用。

---

# 38. 标题必须保留特殊读法

任何地方出现正式日文标题时：

优先使用：

```text
そして〖只因｜チキン〗もいなくなった
```

而不是：

```text
そしてチキンもいなくなった
```

也不要替换为：

```text
そして鶏もいなくなった
```

因为：

> “写作只因，读作チキン”

本身就是标题的一部分。

---

例如：

```yaml

  type: dialogue
  speaker: chinatsu
  ja: "あの……それ、もらってもいいですか？"
```

投入配音或 Ren'Py 后不重新编号。

# 45. 立绘

采用：

```text
character
+
costume
+
expression
```

例如：

```text

qixing / police / neutral

chinatsu / casual / weak
chinatsu / casual / embarrassed
chinatsu / dress / cry
```

---

# 46. 徐启星立绘可以正常出现

Narrative POV 不限制 Visual POV。

普通 Scene 完全可以：

```text

右：千夏
```

徐启星也可以出现在：

- CG
- 群像
- 双人画面
- 远景
- 电影化镜头

---

# 47. CG

CG 在章节台本完成后决定。

适用于：

- 关键剧情转折
- 情绪高潮
- 重要登场
- 悬疑揭示
- 强烈动作
- 普通立绘无法表现的场景
- 特别值得留下印象的喜剧画面

CG 镜头完全自由。

---

# 48. BGM

先使用功能分类：

```text

daily_comedy
warm
romantic_soft
mystery_low
mystery_dark
danger
sad
revelation
climax
```

具体曲目在 Scene 制作时选择。

不要频繁切歌。

---

# 49. SE

用于增强：

- 空间感
- 动作
- 节奏
- 喜剧
- 悬疑
- 冲击
- 环境

不要让每一个动作都有音效。

---

# 50. 外部素材许可

BGM、SE、字体等外部素材必须记录：

```text
素材名称
作者
来源
许可证
署名要求
是否允许修改
是否允许随游戏重新分发
```

许可不明确的素材不要进入正式版本。

> 运行和演出层。

> 正式文本源。

关系必须保持：

```text
日语台本
↓
Ren'Py 实装
```

# 65. 阶段状态与续作入口

开始工作时先检查已有成果，判断当前阶段，不因更换 Agent 或开启新会话而重复初始化、覆盖已完成内容。

第一阶段的完成条件：

- 完整阅读当前版本的 `source/novel.txt`。
- `docs/story_overview.md` 包含第 18 节要求的内容，并区分事实、角色说法和未解疑点。
- `docs/chapter_plan.md` 的原文范围连续覆盖全书，且没有展开全书 Scene 或资产。
- 两份文档记录来源路径、原文 SHA-256 与范围定位方式。

原文版本未变时可以复用已完成的全文理解；开始具体 Chapter 时仍须重读其对应原文。原文版本改变时先核对变更影响，必要时重新阅读全文，再更新总览及章节边界。禁止 Agent 修改小说以消除矛盾。

阶段完成状态暂记在既有规划文档末尾，不为第一阶段新增状态文件。第一阶段完成不等于获准制作 Chapter 1；视觉风格、章节制作和后续章节按用户指定范围推进。

# 66. 剧情证据与不确定性

剧情总览和章节研究中，明确区分：

- 原文明示的事件。
- 人物口述、推测、回忆或日记中的说法。
- Agent 的改编判断及尚未解释的矛盾。

重要事实与疑点记录原文节号、行号或内容锚点。行号仅对所记录的原文版本有效。不能把“角色计划这样做”写成“已经全部成功实施”，也不能为了补齐因果而擅自新增身份、死亡、动机或世界观。

有明确上下文的姓名笔误可以在台本中统一，但需保留原文定位；影响人物身份、案件结论或结局的歧义应保留并向用户提出，不得默默修正。此类原文研究资料不进入汉化输入包。

# 67. 台本结构与视点声明

制作第一个 Chapter 时，在 `script_ja/chXX.yaml` 使用以下层级；后续章节保持一致。第一阶段不提前创建台本文件。

```yaml
schema_version: 1
chapter_id: ch01
scenes:
  - id: ch01_sc01
    scene_kind: main
    narrative_pov: qixing
    location: example_location
    time: example_time
    entries: []
```

- `scene_kind` 为 `main` 或 `side_scene`。`side_scene` 是 Scene 属性，不是对白类型。
- 普通 Scene 的 `narrative_pov` 为 `qixing`；特殊 Scene 明确填写其他角色 ID，或以 `external` 表示仅呈现外部行为的视点。
- 同一 Scene 的视点保持明确；需要进入另一角色内心时，划出带标记的特殊段落／Scene，不能无提示切换。
- 视点字段只约束叙事可知信息，不限制镜头，也不限制徐启星出现在画面中。
- 徐启星不在场的重要事件可以通过特殊 Scene 或具有明确来源的报告表达，不能直接搬进他的亲历独白。

`entries` 按播放顺序混排显示文本与演出指令：

- `dialogue`：非徐启星角色的说出口对白，必填 `speaker`、`ja`，默认配音。
- `protagonist_dialogue`：徐启星说出口对白，`speaker: qixing`，必填 `ja`，不配音。
- `thought`：视点人物内心，必填 `speaker`、`ja`，不配音；普通 Scene 的说话者为 `qixing`，特殊 Scene 必须与其视点人物一致。
- `direction`：不显示、不配音的演出指令，填写 `action` 与必要参数，可记录表情、动作、停顿、转场及声音提示；不得将应呈现的关键信息只藏在制作备注中。
- 普通 Scene 不引入 `narrator`。确有特殊文字载体（如日记、手机消息）时，在首次使用前明确其类型、来源和配音规则，不伪装成普通说出口对白。

每条显示文本沿用稳定 Line ID。演出指令使用独立命名空间，如 `ch01_sc01_dir001`，避免消耗或混淆文本 ID。演出备注不是正式日语文本，不得误送配音或汉化。

# 68. Ruby 显示、朗读文本与专名

日语显示文本 `ja` 可以使用项目约定的 `〖表记｜读音〗` 标记，例如 `〖只因｜チキン〗`。这是台本表示法；实装层负责转换为 Ren'Py 的 Ruby 表示，不能把这些分隔符直接展示给玩家或送入语音合成。

有配音的台词可提供 `ja_spoken` 作为显式朗读文本。没有该字段时，由 `ja` 推导：普通文字保持不变，Ruby 取读音，去除显示专用标记。两者表达同一条台词，不允许分别改写剧情。

专名的固定读法在 `docs/character_language.md` 中随角色制作逐步登记；汉化所需的固定译名另写入 `docs/localization_guide.md`。不要仅凭罗马字角色 ID 推断人物日语读法。标题必须保留“只因”的视觉表记。

在投入配音前检查：Ruby 成对且无空读音、朗读文本没有残留显示标记、专名读法一致、徐启星台词与所有内心没有生成 voice。

# 69. 汉化的上下文隔离

“汉化阶段不读取原文”还包括避免沿用已经包含小说原句的会话上下文。正式汉化应在未读取原文的独立上下文中进行；不能声称同一上下文只靠不再次打开文件就实现了隔离。

汉化只提供：

- 当前需要汉化的日语正式台本及理解它所需的日语上下文。
- 不含对应小说原句的 `docs/localization_guide.md`。
- 必要的显示限制、角色 ID 与 Line ID。

不提供 `source/novel.txt`、故事总览、带原文摘录的计划、原文对照表或含这些内容的历史对话。只提供执行任务必需的输入，不继承全文历史。若当前工作环境无法做到隔离，明确说明并另行安排独立上下文，不把受原文影响的重译标成隔离汉化。

剧情忠实度审核在日语改编阶段对照原文进行；汉化质量审核对照日语进行。修改日语台本来修复剧情后，再依据更新后的日语更新汉化，不能直接拿中文原句回填字幕。

本节规定输入边界，不要求每次任务都启用多 Agent，也不要求在第一阶段创建汉化任务。

# 70. 稳定 ID 与修改联动

Line ID 是身份，不是显示顺序。投入配音或实装后：

- 已有台词保留 ID，顺序由 `entries` 列表决定；插入台词使用本 Scene 尚未用过的新 ID，不重新编号后续台词。
- 删除的 ID 不回收；拆分或合并台词若已改变原条目的身份，分配新 ID，旧 ID 标记停用，检查所有引用。
- Scene ID 同样不因插入或排序而整体重排。
- 修改正式文字先改日语台本，不能只在 Ren'Py 或字幕副本里修改而留下两个文本源。

从首次生成下游产物开始，在当前 Chapter 的制作计划中记录其对应台本版本或内容摘要值、状态（待生成／待更新／已核验）与输出位置。可以先用简表维护，不必在第一阶段搭建自动化系统。

| 修改内容 | 必须复核或更新的产物 |
|---|---|
| `ja`、文字类型或 speaker | 汉化、实装；复核朗读文本、语音归属和是否需要重录 |
| `ja_spoken`、读音或配音演技 | 对应语音及播放效果；如果含义变化，同步检查显示文本和汉化 |
| 仅显示排版或 Ruby 表记、读音未变 | 双语布局与实装；不强制重录未变化的语音 |
| 表情、动作、镜头或声音指令 | 对应演出与资产引用；改变语境时再复核台词和译文 |
| ID、文件路径、资源命名 | 所有相关引用、语音和字幕映射，避免错配或失效 |

原文版本变化时先复核日语改编，再沿依赖关系更新；不得直接以原文覆盖汉化。只更新受影响部分，不为无关改动重做整章素材。

# 71. 章节验收与受阻记录

第 59 节的人工 QA 之外，正式制作时增加必要的结构检查：

- 台本能解析，必填字段存在，角色 ID 合法，Scene ID／Line ID 唯一。
- 普通 Scene 的内心视点正确，没有独立第三人称旁白。
- 显示文本、语音、字幕和 Ren'Py 通过稳定 ID 对应；无缺失引用、停用 ID 引用或已过期产物被误用。
- 徐启星对白、所有内心、系统与 UI 文本符合不配音规则。
- Ruby 显示与实际朗读一致；双语文本无溢出，实际游戏能顺序运行到本章结束。
- 正式外部素材有明确许可；语音模型权重、所用字体和音频均核对各自适用许可，不能只依据工具本身的许可证。

仅写完台本、仅准备 prompt、或仅列出配音计划不能标为整章完成。缺少模型、运行环境或正式素材时，记录已完成部分、具体缺口及下一步；可以继续不依赖缺口的工作，但不能用占位资源冒充最终成果。

检查按当前阶段和实际变更执行，不在第一阶段提前搭建测试工程，不为无关内容反复运行检查。
